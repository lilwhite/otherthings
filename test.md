I’ve completed the initial investigation around the Azure Monitor retirement advisory.
The affected subscription is Santander Management - Basefarm CSP. I identified 4 legacy NSG Flow Logs in West Europe, all with Traffic Analytics enabled and sending data to the Log Analytics workspace scb-core-mgt-network-log-law. The related tables AzureNetworkAnalytics_CL and AzureNetworkAnalyticsIPDetails_CL are still shown as Custom table (classic).
I also ran Microsoft’s official NSG Flow Log migration script in analysis mode only, so no changes were made. The analysis correctly detected the 4 existing NSG Flow Logs and proposed their migration to Virtual Network Flow Logs.
Regarding the timelines:
- Data Collector API – 14 September 2026: this is a support retirement date, not a hard technical cut-off. Existing ingestion using TLS 1.2+ is expected to continue working after that date, although the API becomes legacy/out of support.
- NSG Flow Logs – 30 September 2027: this is the separate retirement date for NSG Flow Logs, which should be migrated to Virtual Network Flow Logs before then.
I’ve also been reviewing the available repositories to identify where these resources are created and managed. So far, I haven’t been able to find any Terraform resource definition for the current MGT NSG Flow Logs. I can only find references to existing network resources through Terraform data blocks, so those parts of the code are consuming already existing Azure resources rather than creating them. I also checked the Git history and found an old STG network-watcher-flow-log.tf, but nothing equivalent for the current MGT Flow Logs.
My proposed next step would therefore be to confirm with the platform/network team whether these 4 Flow Logs are managed by another repository, pipeline, Azure Policy or any other IaC/automation.
If they are not managed by IaC, the first option would be to use Microsoft’s official migration script to migrate them from NSG Flow Logs to Virtual Network Flow Logs. If they are managed by IaC, the migration should instead be implemented through the corresponding repository/module to avoid configuration drift.
At this stage there is no immediate service interruption expected on 14 September 2026, and no migration changes have been applied yet.
